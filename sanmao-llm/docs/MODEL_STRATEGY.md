# 模型策略说明：Claude API、传统 ML、风控怎么分工

这份文档回答几个核心问题：

1. 为什么不直接全部用 Claude/OpenAI API？
2. 为什么文本抽取用 Claude API 而不自部署模型？
3. 为什么还需要 XGBoost/LightGBM 这类传统 ML？
4. 金融公司一般怎么做？
5. `sanmao-quant-llm` 当前用哪个模型？

## 先给结论

当前项目走**混合模式，但 LLM 部分直接用 Claude API，不自部署模型、不需要 GPU**：

```text
Claude API：用于代码助手、研究辅助、新闻/文本结构化特征抽取
传统 ML：用于最终可回测、可验证的预测模型
规则/风控：用于决定能不能下单、下多少、何时停止
```

一句话：

```text
LLM（Claude API）做“理解文本和生成特征”
传统 ML 做“学习历史规律和输出概率”
风控/策略层做“是否买卖”
```

> 早期版本曾计划在 GPU 上自部署 Qwen 做文本抽取。现在改为直接调用 Claude API：
> 本机已经装了 Claude，直接用 API 更省事，不必维护 GPU/模型权重/推理栈。历史自部署经验见
> [docs/LLM_DEPLOYMENT_NOTES.md](LLM_DEPLOYMENT_NOTES.md)（已归档，仅供参考）。

## 为什么不全部用 Codex/Claude/OpenAI API

API 的优点：

1. 模型强，尤其是复杂推理、写代码、解释、摘要。
2. 不需要自己维护 GPU。
3. 不占本地磁盘。
4. 能快速试错。

API 的缺点：

1. 成本随调用量增长，批量跑新闻/舆情可能很贵。
2. 数据会离开自己的服务器，需要考虑隐私、合规、供应商风险。
3. 网络延迟和 API 限流不可控。
4. 不能保证某个模型版本长期不变。
5. 交易系统需要可审计、可复现，纯 API 黑箱不够稳。

所以 API 适合：

```text
写代码
解释报错
生成研究思路
少量新闻摘要
非敏感文本分析
```

不适合一开始就直接负责：

```text
高频批量特征生产
敏感交易逻辑
真实账户自动下单
不可审计的最终买卖决策
```

## 用 Claude API 做文本特征抽取

用 Claude API 抽取文本特征，价值在于：

1. 不用维护 GPU、不占本地磁盘、不管推理栈。
2. 用 structured outputs 固定输出 schema（固定 JSON），下游特征稳定。
3. 批量抽取默认用便宜的 `claude-haiku-4-5`，成本可控；结果落地 CSV 复用，不重复调用。
4. 需要更强理解时，一行参数就能换 Sonnet/Opus。

Claude API 适合做：

```text
新闻结构化
公告事件抽取
情绪/风险标签
研报摘要
实体识别和 ticker linking
```

不建议让 LLM 直接做：

```text
今天买什么
买多少
什么时候卖
是否重仓
```

> 早期曾权衡“自部署 vs API”，理由包括数据不出服务器、固定模型版本、不受限流等。
> 当前决策是直接用 Claude API（本机已装 Claude，省去 GPU 运维）。如果未来出现强隐私/合规约束，
> 再评估自部署；历史自部署经验见 [docs/LLM_DEPLOYMENT_NOTES.md](LLM_DEPLOYMENT_NOTES.md)（已归档）。

这些必须交给可回测的模型、策略和风控层。

## 为什么还需要传统 ML

传统 ML 指：

```text
XGBoost
LightGBM
RandomForest
Logistic Regression
PyTorch 时间序列模型
```

它们的价值是：

1. 输入是明确的表格特征。
2. 输出是概率或收益预测。
3. 可以严格 walk-forward 回测。
4. 可以评估 AUC、log_loss、收益、回撤、换手率。
5. 可以比较不同特征是否真的有用。
6. 比 LLM 更适合做“历史统计关系学习”。

LLM 擅长语言理解，不擅长可靠地从历史样本里稳定学习交易边际。

举例：

```text
LLM：这条新闻是 AAPL 财报，情绪 -0.2，风险是 margin_pressure
ML：历史上类似“财报 + 轻微负面 + 毛利率压力 + 当前价格趋势”的组合，下一天上涨概率是多少
策略：如果概率超过阈值，并且风险限制允许，就 long
```

所以传统 ML 不是多余的，它是把 LLM 文本理解变成可验证交易系统的桥。

## 金融公司一般怎么做

不同公司差异很大，但成熟金融机构通常不会只靠一个大模型直接交易。

更常见的是混合架构：

1. 传统量化模型仍然是核心预测和组合构建工具。
2. LLM 用于研究、代码、文档、新闻/公告/研报结构化、客服和运营。
3. 敏感数据会放在受控环境，使用企业 API、私有云、内网部署或自部署模型。
4. 关键模型要做模型风险管理（model risk management）、验证、审计和监控。
5. 第三方模型/API 要纳入供应商风险和数据治理。

这也是为什么我们要保留：

```text
数据版本
特征定义
训练窗口
回测结果
模型参数
输出日志
```

金融系统要能解释“为什么当时会给出这个信号”。

## 我们这个项目的推荐模式

当前阶段采用：

```text
Claude API 辅助开发 + 本机工程回测 + Claude API 文本特征 + 传统 ML 预测
```

更具体：

| 模块 | 推荐方式 | 原因 |
|---|---|---|
| 写代码/解释问题 | Claude API | 速度快，模型强 |
| 新闻/公告批量结构化 | Claude API（默认 `claude-haiku-4-5`） | 便宜、无需维护 GPU、schema 可控 |
| 价格/文本特征预测 | XGBoost/LightGBM/scikit-learn | 可回测、可验证 |
| 最终买卖 | 策略 + 风控规则 | 不能让 LLM 直接下单 |
| 真实账户 | 最后阶段接入 | 必须先 paper trading |

## 关于模型选择

不需要下载任何本地大模型。抽取器直接调 Claude API：

- 默认 `claude-haiku-4-5`：批量抽新闻便宜、快、结构化足够。
- 质量优先时用 `--model claude-sonnet-5` 或 `--model claude-opus-4-8`。
- 没有 key / 想跳过 API 时，用 `--rule-fallback-only` 跑规则抽取器验证下游链路。

## 当前推进顺序

当前最短板不是“模型不够强”，而是数据和链路：

1. 真实市场数据还没稳定接入。
2. 文本数据源还没接入。
3. LLM 文本特征表还没建全。
4. 回测还只是 baseline。
5. 还没有 paper trading。

正确顺序应该是：

```text
真实市场数据
  -> 稳定特征库
  -> baseline 回测
  -> LLM 文本特征（Claude API 抽取）
  -> 对比“有无 LLM 特征”的提升
  -> paper trading
  -> 小权限实盘
```
