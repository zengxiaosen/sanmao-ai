# 模型策略说明：API、自部署 LLM、传统 ML 怎么分工

这份文档回答几个核心问题：

1. 为什么不直接全部用 Codex/Claude/OpenAI API？
2. 为什么还要自己部署大模型？
3. 为什么还需要 XGBoost/LightGBM/PyTorch 这类传统 ML？
4. 金融公司一般怎么做？
5. `sanmao-quant-llm` 当前应该下载几个模型？

## 先给结论

当前项目不应该一开始下载多个 32B 大模型，也不应该一开始接真实股票账户。

推荐架构是混合模式：

```text
外部 API：用于代码助手、研究辅助、低敏文本理解
本地 LLM：用于敏感数据、可控成本、批量文本特征抽取
传统 ML：用于最终可回测、可验证的预测模型
规则/风控：用于决定能不能下单、下多少、何时停止
```

一句话：

```text
LLM 做“理解文本和生成特征”
传统 ML 做“学习历史规律和输出概率”
风控/策略层做“是否买卖”
```

## 为什么不全部用 Codex/Claude/OpenAI API

API 的优点：

1. 模型强，尤其是复杂推理、写代码、解释、摘要。
2. 不需要自己维护 GPU。
3. 不占本地磁盘。
4. 能快速试错。

API 的缺点：

1. 成本随调用量增长，批量跑新闻/舆情可能很贵。
2. 数据会离开自己的服务器，需要考虑隐私、合规、供应商风险。
3. 网络延迟和 API 限流不可控。
4. 不能保证某个模型版本长期不变。
5. 交易系统需要可审计、可复现，纯 API 黑箱不够稳。

所以 API 适合：

```text
写代码
解释报错
生成研究思路
少量新闻摘要
非敏感文本分析
```

不适合一开始就直接负责：

```text
高频批量特征生产
敏感交易逻辑
真实账户自动下单
不可审计的最终买卖决策
```

## 为什么还要自部署 LLM

自部署 LLM 的价值不是“它一定比 Claude 更聪明”，而是：

1. 数据留在自己服务器。
2. 批量跑文本特征时成本更可控。
3. 可以固定模型版本，回测更可复现。
4. 可以把输出 schema 固定下来，比如固定 JSON。
5. 对新闻/公告/研报做大批量离线处理时，不受 API 限流影响。

自部署 LLM 适合做：

```text
新闻结构化
公告事件抽取
情绪/风险标签
研报摘要
实体识别和 ticker linking
```

不建议让自部署 LLM 直接做：

```text
今天买什么
买多少
什么时候卖
是否重仓
```

这些必须交给可回测的模型、策略和风控层。

## 为什么还需要传统 ML

传统 ML 指：

```text
XGBoost
LightGBM
RandomForest
Logistic Regression
PyTorch 时间序列模型
```

它们的价值是：

1. 输入是明确的表格特征。
2. 输出是概率或收益预测。
3. 可以严格 walk-forward 回测。
4. 可以评估 AUC、log_loss、收益、回撤、换手率。
5. 可以比较不同特征是否真的有用。
6. 比 LLM 更适合做“历史统计关系学习”。

LLM 擅长语言理解，不擅长可靠地从历史样本里稳定学习交易边际。

举例：

```text
LLM：这条新闻是 AAPL 财报，情绪 -0.2，风险是 margin_pressure
ML：历史上类似“财报 + 轻微负面 + 毛利率压力 + 当前价格趋势”的组合，下一天上涨概率是多少
策略：如果概率超过阈值，并且风险限制允许，就 long
```

所以传统 ML 不是多余的，它是把 LLM 文本理解变成可验证交易系统的桥。

## 金融公司一般怎么做

不同公司差异很大，但成熟金融机构通常不会只靠一个大模型直接交易。

更常见的是混合架构：

1. 传统量化模型仍然是核心预测和组合构建工具。
2. LLM 用于研究、代码、文档、新闻/公告/研报结构化、客服和运营。
3. 敏感数据会放在受控环境，使用企业 API、私有云、内网部署或自部署模型。
4. 关键模型要做模型风险管理（model risk management）、验证、审计和监控。
5. 第三方模型/API 要纳入供应商风险和数据治理。

这也是为什么我们要保留：

```text
数据版本
特征定义
训练窗口
回测结果
模型参数
输出日志
```

金融系统要能解释“为什么当时会给出这个信号”。

## 我们这个项目的推荐模式

当前阶段采用：

```text
API 辅助开发 + 本地工程回测 + 后续本地 LLM 文本特征 + 传统 ML 预测
```

更具体：

| 模块 | 推荐方式 | 原因 |
|---|---|---|
| 写代码/解释问题 | Codex/Claude/API | 速度快，模型强 |
| 新闻/公告批量结构化 | 本地 14B/32B LLM 或企业 API | 数据和成本可控 |
| 价格/文本特征预测 | XGBoost/LightGBM/PyTorch | 可回测、可验证 |
| 最终买卖 | 策略 + 风控规则 | 不能让 LLM 直接下单 |
| 真实账户 | 最后阶段接入 | 必须先 paper trading |

## 当前到底要下载几个大模型

服务器数据盘只有 50GB，所以不要一次下载多个 32B。

当前建议：

```text
先下载 0 个大模型，先把市场数据和回测跑通。
市场数据链路稳定后，只下载 1 个主力 LLM。
```

候选模型：

### 方案 A：先下载 Qwen3-14B 或 14B 量化版

适合：

```text
先跑新闻结构化
省磁盘
省显存
速度更快
```

这是我当前更推荐的第一步，因为你的数据盘只有 50GB。

### 方案 B：下载 Qwen3-32B-AWQ

适合：

```text
更强的中文/英文理解
更强的结构化抽取
48GB 显存可跑
```

问题：

```text
模型体积较大，50GB 数据盘会很紧
```

### 方案 C：DeepSeek-R1-Distill-Qwen-32B

适合：

```text
复杂推理
研报式分析
事件归因
```

不适合作为第一阶段高频新闻批处理模型，因为 reasoning 模型通常更慢、更贵。

### 方案 D：Qwen2.5-Coder-32B

适合：

```text
本地写代码模型
```

但我们已经可以用 Codex/Claude 辅助写代码，所以它不是当前优先级。

## 当前下载决策

当前不立即下载 3 个大模型。

推荐优先级：

1. 先把真实市场数据接入跑通。
2. 再下载一个轻一点的文本抽取模型，优先 14B 级别。
3. 如果效果不够，再升级到 32B AWQ。
4. DeepSeek-R1-Distill-Qwen-32B 和 Qwen2.5-Coder-32B 暂时不下载。

当前下载清单：

```text
已下载大模型：0 个
下一步建议下载：1 个文本抽取模型
暂不下载：DeepSeek-R1-Distill-Qwen-32B、Qwen2.5-Coder-32B
```

对应脚本：

```bash
bash scripts/env/download_llm_model.sh qwen3-14b-awq
```

这个脚本不会自动下载，必须显式传入模型 alias。这样可以避免误下载多个大模型，把 50GB 数据盘占满。

## 为什么这个决策更适合现在

因为当前最短板不是“大模型不够强”，而是：

1. 真实市场数据还没稳定接入。
2. 文本数据源还没接入。
3. LLM 文本特征表还没建。
4. 回测还只是 baseline。
5. 还没有 paper trading。

如果现在先下载多个大模型，会占用时间、磁盘和 GPU 费用，但不一定推进交易系统核心能力。

正确顺序应该是：

```text
真实市场数据
  -> 稳定特征库
  -> baseline 回测
  -> LLM 文本特征
  -> 对比“有无 LLM 特征”的提升
  -> paper trading
  -> 小权限实盘
```
